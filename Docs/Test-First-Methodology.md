# Proportionate development and validation

Supra AI uses tests to support delivery, not to create a second project around every change.
The goal is to finish a plan with enough evidence to merge and release the same commit without
repeating equivalent checks.

## Plan once

For substantial work, keep one lightweight working plan containing:

- the user-visible outcome and non-goals;
- the implementation tasks;
- the focused tests or checks that prove the change; and
- a short definition of done.

The plan may live in the active agent/task workspace and need not be committed. Separate SPEC,
PLAN, TESTPLAN, work-order, sign-off, and progress-ledger documents are optional. Use them only
for work where the extra artifact resolves real ambiguity or risk, such as a destructive data
migration, a trust-boundary change, or a new release protocol.

## Test the behavior that changed

Add or update focused tests for behavioral changes. Tests may be written before or alongside
the implementation and may land in the same coherent commit. A separate failing-test commit,
recorded RED reason, and human RED/GREEN sign-off are not required.

Tests must still be meaningful:

- exercise the actual changed path and assert an observable result;
- use non-default values when proving configuration or wiring;
- fail loudly instead of silently returning or skipping;
- avoid tautologies and assertions on fixtures the production path never reads; and
- compare against independent fixtures or frozen goldens, never a golden generated by the
  code under test in the same run.

Fixes should include a regression test when one is practical and stable. Do not add a brittle
UI test merely to restate behavior already proven at a lower, more reliable seam.

## Validate by impact

Use the smallest useful loop during implementation, then run one final pass after the relevant
code has stopped changing.

| Change | Normal final validation |
| --- | --- |
| Documentation or copy only | link/content check or no automated test |
| Isolated package logic | affected package tests |
| App UI or composition | affected package tests plus one relevant app build or focused UI check |
| Cross-package or dependency change | affected dependency cone plus app build |
| Migration, persistence, security boundary, or release machinery | focused safeguards plus the broader suites uniquely needed for that risk |

The selected hosted CI run is the final merge and release-readiness receipt for its exact SHA.
Do not also require a blanket local all-package run, a second identical run after merge, or a
generic smoke suite unrelated to the change. Repeat a successful check only when relevant code,
inputs, dependencies, toolchain, or environment changed, or when the first result was invalid.

## Report evidence plainly

At completion, record what ran, its result, and any material scope that could not be verified.
Inspection is useful but is not a substitute for a required macOS/Xcode check. An unavailable
optional check is a disclosed limitation, not a reason to invent another gate.

Synthetic fixtures only: never use client data. When a golden intentionally changes, explain
why the expected output changed in the commit or change summary.
